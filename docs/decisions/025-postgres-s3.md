# ADR-025. PostgreSQL и S3: разбор перед началом (B9)

- **Статус:** предложено — **ждёт решения автора** (этап 6, шаг B9; PLAN.md 1.2)
- **Связано:** ADR-004 (этап 1: SQLite и папка вместо PostgreSQL и S3), ADR-011 (ПК школы), ADR-015

## Зачем этот разбор

В плане этапа 6 записано: «PostgreSQL — последним, отдельной веткой, перед началом — отдельный
разбор шага; вливаем только при полностью зелёном на обеих базах». Ниже — что показал разбор кода
и какие есть пути. Код по B9 не писался: выбор пути — архитектурное решение (CLAUDE.md §9.2).

## Что показал разбор

### База

- Весь сервер написан на **синхронном** better-sqlite3: **418 запросов** (`.get()` 134, `.all()` 103,
  `.run()` 181) в 34 файлах, **27 транзакций** (95 запросов внутри них). У драйвера PostgreSQL нет
  синхронного режима: каждый запрос становится `await`, а каждая функция с запросом — `async`.
- Синхронность держит многое, кроме самих запросов:
  - проверка учителя на **каждом** запросе (`onRequest` → `readTeacher`);
  - 78 проверок доступа (`requireClass`, `requireSchoolAdmin` …) в 17 файлах — внутри синхронных
    обработчиков;
  - хранилище контента (`ContentStore`: `getLesson`, `getPractice` …) читает уроки учителей из
    базы синхронно — 29 вызовов в 9 файлах;
  - урок в реальном времени: сообщение WebSocket → `store.dispatch` → запись активности, ответов,
    посещаемости — синхронно и **по порядку**; таймеры этапов (`finish` → `markAbsent` → сдача
    практики в транзакции); `flush` при закрытии сервера;
  - запросы внутри `map`/`flatMap` (КТП, отчёты, журнал);
  - последовательности «прочитать — проверить — записать» (квота файлов, счётчик приглашения,
    свободный код урока), которые сейчас атомарны «бесплатно», а на PostgreSQL требуют блокировок.
- better-sqlite3 **не принимает async-транзакции**: общий асинхронный код на двух базах требует
  либо асинхронного драйвера SQLite (`@libsql/client`), либо своей обёртки транзакций.
- Схема: 31 таблица на `sqlite-core`. Drizzle не умеет одну схему на два диалекта — нужна вторая
  (`pg-core`) и тест их равенства; миграции — две папки (сейчас 21 миграция SQLite).
- Отличия SQL небольшие: `max(a, b)` → `GREATEST` (sync/receive.ts), `sum()` в PostgreSQL —
  строка (student-files.ts). Но **порядок строк**: только 37 `orderBy` на 418 запросов — код местами
  полагается на порядок вставки; сортировка кириллицы и `NULL` в PostgreSQL другая.
- Тесты: 47 файлов, 104 прямых синхронных обращения к базе в 21 из них.

### Файлы

- Работы учеников (по хэшу), скриншоты, файлы уроков, обновления — около 30 мест в 8 модулях.
- Часть — потоками (загрузка, отдача), часть — синхронно (`writeFileSync`, `rmSync` в `collect`,
  который вызывается из 14 мест, в том числе из транзакций). S3 тоже только асинхронный, поэтому и
  перенос файлов задевает те же синхронные цепочки, хотя и меньше.

## Варианты

### 1. Полный переход: один асинхронный код на SQLite и PostgreSQL

- Все запросы — `await`; SQLite — через `@libsql/client` (асинхронные транзакции); вторая схема
  `pg-core` и тест равенства; две папки миграций; CI гоняет тесты на обеих базах (PostgreSQL в
  `docker-compose` и сервис CI).
- Переделать `ContentStore` на кэш уроков (иначе асинхронность расползётся по 29 вызовам),
  проверки доступа — на `preHandler`, урок в реальном времени — на очередь записи, чтобы порядок
  событий сохранился.
- Файлы — интерфейс хранилища (папка / S3 через лёгкую подпись SigV4, например `aws4fetch`).
- **Объём:** несколько рабочих дней сосредоточенной работы и большая регрессия: затрагивается почти
  каждый файл сервера и урок в реальном времени. Вливать — только после полного прогона всех
  сквозных сценариев и проверки класса на ПК.

### 2. Сейчас — SQLite и на сайте, PostgreSQL — по признакам роста (рекомендую)

- Сайт остаётся на SQLite (один процесс, WAL): для пилота из нескольких школ этого с запасом
  хватает — нагрузка в основном чтение, записи мало.
- **Надёжность данных** решается непрерывной копией базы в S3-совместимое хранилище (Litestream —
  отдельный процесс рядом с сервером, без изменений кода) и ежедневным снимком.
- Файлы — в S3 по варианту 1 (это меньшая и отдельная задача), когда сайт переедет на сервер в
  Узбекистане.
- **Когда переходить на вариант 1:** нужен второй процесс сервера (несколько машин за
  балансировщиком), база больше нескольких ГБ, или запись начинает мешать уроку.
- **Объём:** 0,5–1 день (Litestream в `deploy/`, инструкция восстановления, проверка).

### 3. PostgreSQL только на сайте, SQLite только на ПК — две сборки

- Отпадает: код всё равно пришлось бы сделать асинхронным и держать две схемы — та же работа, что
  в варианте 1, плюс две сборки.

## Что нужно от автора

Выбрать вариант 1 или 2 (или назвать признаки, при которых переходить). До решения шаг B9 не
начинается; ветка `claude/stage6-postgres` создаётся вместе с первым коммитом выбранного варианта.
